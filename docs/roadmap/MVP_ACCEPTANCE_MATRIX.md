# MVP Acceptance Matrix

本文把 [REQUIREMENTS](../../REQUIREMENTS.md) 中“满足原始全量需求的最小版本”转换为
可重复验收的门禁。它不把 schema、文档、local adapter、fake detector 或相邻仓库
已有组件写成 Argus 的生产能力。

状态口径：

- `verified`：当前生产路径实现了本行全部最小验收，测试证据可重复；
- `partial`：只有子能力，或只有经过测试的 local adapter/fake；
- `missing`：没有可执行实现；仅有文档或类型也归此类；
- `externally-blocked`：Argus 侧仍需 contract/adapter，但最终验收还依赖 Hailix 或
  Eino-Agent 的外部能力。

文中 `local verified` 只说明本地 adapter 已通过测试，不代表多租户、分布式或生产
隔离已经成立。当前证据日期为 2026-08-27。

同日新增的 `evaluation corpus` formal baseline runner 已减少 R-CORE-004/R-EVAL-001 的编排缺口：它先用
content-addressed `CorpusSnapshot` 冻结完整 Case/source execution closure，并以 purpose/single-split、
clone-group 去重和 holdout 全历史 exposure 门禁隔离语料，再消费 independently governed
active Case，并整体重验 source snapshot、label revision、evaluation eligibility、
holdout exposure authority 与 remote-write deny，再使用稳定 formal key 执行每个 Case；checkpoint 后自动由
committed governed report 生成 EvaluationRun，exact retry/resume 不重跑 provider。当前证明来自两 source
fake-provider CLI E2E，以及一个真实 Hailix/DeepSeek `inconclusive` diagnostic；后者 0 Candidate 且 coverage
partial，不能计为通过，参与后续诊断的 clone 也不能继续作为 blind holdout。尚不是多仓真实
precision/recall/repeatability/cost corpus，因此两行仍保持 `partial`。

## Completion gates

以下 gate 按依赖顺序执行。前一 gate 未通过时，后一 gate 的成功不能用于宣布 MVP
完成。

1. **G0 当前基线不回退**
   - `make verify` 全绿；
   - diff、selection、overlay、scope 的 local acceptance fixtures 可重复；
   - local/fake 输出持续标注其 adapter/runtime identity。
2. **G1 Target 与配置冻结**
   - R-CORE-001、R-CONFIG-001~003 达到 `verified`；
   - 已落地的 symbol/multi-range selection 保持回归门禁；补齐 ContextRef provider/
     ContextGap 和 production effective-config explain 验收；
   - ConfigBundle/RulePack 发布与回滚后，旧 run snapshot 不漂移。
3. **G2 Snapshot 与权威数据闭包**
   - R-CORE-002、R-DATA-001~003 达到 `verified`；
   - authority-aware Artifact resolver、完整 ExecutionSnapshot、quarantine/tombstone、
     PostgreSQL/ObjectStore projection 均通过重启和损坏注入。
4. **G3 完整 DAG 与持久执行**
   - R-CORE-003、R-CORE-005、R-CORE-007 领域部分达到 `verified`；
   - 九个领域逻辑阶段加 report presentation stage 的 DAG、生命周期 ledger、
     shard/checkpoint、cancel fence、lease/reconciler、workload/backpressure fault tests
     全绿。
5. **G4 安全平台执行**
   - Hailix 和 Eino-Agent 两行达到 `verified`；
   - immutable platform binding、typed result/Trace、review-safe profile、外部隔离和
     恶意仓库测试全部通过；
   - DirectTaskInput/local fake 不计入此 gate。
6. **G5 真实评审与离线评测**
   - R-CORE-004、R-EVAL-001~003 和 NFR 达到 `verified`；
   - 多 detector 组合、受治理数据集、污染防护和单变量原子 replay 使用同一 stage
     implementation；
   - 建立真实基线，但此时仍保持远程发布关闭。
7. **G6 发布安全与 Promotion**
   - R-CORE-006、R-EVAL-004 达到 `verified`；
   - shadow、canary、unknown-outcome reconcile、rollback 和安全 fault tests 通过后，
     才能按版本化 policy 开启受限远程写。
8. **G7 收益闭环**
   - 收益与数据看板达到 `verified`；
   - Feedback、Outcome、ValueObservation 和 E0-E3 证据分层可追溯；
   - dashboard 与离线 export 对账，只有 E2/E3 可进入正式收益/ROI。

只有矩阵全部行达到 `verified`，且 G0~G7 依次通过，才可称为“满足原始全量需求的
最小版本”。M1 local vertical slice 或三仓 smoke 只能作为中间 gate 证据。
